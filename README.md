# Italian Edit

Интернет-магазин брендовой одежды и аксессуаров — [italian-edit.com](https://italian-edit.com).
Люкс-дропшиппинг: сток берётся у поставщика **BrandsGateway** (склады в ЕС и США),
плюс товары, которые менеджер заводит вручную из Италии через Телеграм-бота.

Репозиторий содержит **бэкенд** (`server/`). Сама витрина (тема Shopify) живёт
в Shopify и в репозиторий не входит — её устройство описано в разделе
[«Сайт (витрина Shopify)»](#сайт-витрина-shopify) как справка.

## Из чего состоит проект

| Компонент | Где живёт | Что делает |
|---|---|---|
| **Витрина** | Shopify (тема на базе Horizon) | Сайт, каталог, фильтры, оформление заказа. |
| **Телеграм-бот + сервер** | `server/` (один Node-процесс) | Бот заводит товары из Италии (**канал на паузе**); сервер синкает каталог BG, дотегирует товары под фильтры витрины, снимает метку «новинка», проксирует заказы в BG. |
| **Приложение BrandsGateway** | Shopify App Store | В базовом режиме само заливает сток BG в Shopify, держит остатки и передаёт заказы поставщику. |

Бот и HTTP API — это **один процесс** (`npm run start`): один хостинг, одна кодовая база.

## Два канала поступления товаров

```
┌─ Канал 1: BrandsGateway (массовый сток, ЕС/США) ───────────────────────┐
│                                                                        │
│  IMPORT_MODE=app  (по умолчанию, тариф BG GROW):                       │
│     Приложение BG ──▶ заливает товары в Shopify (теги пола/категории,   │
│                        vendor=бренд), держит остатки, шлёт заказы в BG  │
│     Наш сервер   ──▶ ДОТЕГИВАЕТ склад EU/US (job shopify-tagger)        │
│                                                                        │
│  IMPORT_MODE=api  (тариф BG REST API/CSV):                             │
│     Наш сервер   ──▶ тянет каталог BG в свою БД (job bg-*-sync)         │
│                   ──▶ заливает в Shopify сам (job shopify-push)         │
│                   ──▶ проксирует заказы Shopify → BG                    │
└────────────────────────────────────────────────────────────────────────┘

┌─ Канал 2: Телеграм-бот (ручной, товары из Италии) — НА ПАУЗЕ ──────────┐
│                                                                        │
│  Менеджер пишет в группу:                                              │
│     Название товара / Вариация (цвет) / Дизайнер / Наша цена           │
│     (без вариации — три строки; цена всегда последней)                 │
│  Бот ──▶ находит товар на официальном сайте бренда                     │
│      ──▶ отвечает карточкой (фото, цена бренда зачёркнута, наша цена)   │
│      ──▶ создаёт ЧЕРНОВИК товара в Shopify                             │
│  Менеджер проверяет черновик и публикует                              │
└────────────────────────────────────────────────────────────────────────┘
```

## Два режима импорта BrandsGateway (`IMPORT_MODE`)

Задаётся переменной `IMPORT_MODE` (см. `src/config.ts`).

- **`app`** — *текущий режим.* Тариф BG GROW/Scale, у которого нет REST API.
  Импорт, остатки и заказы делает **приложение BrandsGateway** прямо в Shopify.
  Наш сервер только **дотегивает** товары тем, чего приложение не ставит
  (склад EU/US), и снимает метку «новинка».
- **`api`** — тариф BG REST API/CSV. Всё делает **наш сервер** через API BG
  (`nova.shopwoo.com`): тянет каталог в PostgreSQL, заливает в Shopify,
  проксирует заказы. Требует переменные `BG_*` и `DATABASE_URL`.

> На момент написания у магазина тариф без API, поэтому каталог BG идёт через
> приложение (`app`), а наш `src/bg/*` (прямая интеграция) — на полке.

## Схема тегов — сердце всей системы

Витрина **не** использует Shopify-поле «Product type» или «Category». Вся
навигация, фильтры и умные коллекции держатся на **тегах товаров**. Поэтому
формат тегов обязан совпадать у всех трёх источников (приложение BG, бот, сервер).

| Тег | Что означает | Кто ставит |
|---|---|---|
| `EU` / `US` | Склад отгрузки — коллекции **Ships from Europe/USA** | приложение BG склад НЕ ставит → ставит наш `shopify-tagger` по бренду; бот ставит `EU`; api-push ставит из данных BG |
| `Women` / `Men` | Пол — переключатель **Shop**. Унисекс = оба тега сразу | приложение BG (при импорте), бот (по URL бренда), api-push (из поля gender BG) |
| `Bags`, `Shoes`, `Clothing`, `Accessories`, `Sweaters - Clothing`, … | Категория/подкатегория — пункты меню | приложение BG (свой формат тегов) |
| `category:bags`, `category:dresses`, … | Категория для товаров бота (легаси-формат) | бот (`src/shopify/categorize.ts`) |
| `designer:<бренд>` | Дизайнер (в нижнем регистре) | бот, `shopify-tagger`, api-push |
| `new` | В коллекции **New**; снимается через 14 дней | бот (`NEW_TAG`) |
| `italian-edit` | Коллекция «Italian Edit» (товары бота) | бот (`TG_COLLECTION_TAG`) |
| `delivery:manual-italy` | Доставка ручная из Италии | бот (`TG_DELIVERY_TAG`) |
| `bg` / `tg-bot` | Происхождение товара (BG или бот) | api-push / бот |

Ключевые функции формата — единый источник правды, чтобы теги не разошлись:

- `src/shopify/warehouse.ts` → `warehouseTag("eu") === "EU"`, `warehouseTag("us") === "US"`
- `src/shopify/gender.ts` → `genderTags("women") === ["Women"]`, `"unisex" → ["Women","Men"]`

> **Важно про склад.** Товар с европейского склада продаётся и в США — просто
> едет дольше: склад влияет на сроки доставки, а не ограничивает каталог по географии.
> Переключателя Ships from в шапке больше нет, но теги `EU`/`US` остались — на них
> держатся коллекции Ships from Europe/USA. Приложение BG склад тегом не помечает
> (для него склад — это fulfillment-локация), поэтому склад мы **выводим из бренда**:
> `src/shopify/warehouseByBrand.ts` — известные US-марки (Michael Kors, Coach,
> Tory Burch) → `US`, остальной люкс → `EU`. Список US-брендов — предположение,
> его надо сверять с реальным US-каталогом BG.

## Сервер: переменные окружения

Скопировать `server/.env.example` → `server/.env` и заполнить.

| Переменная | Обяз. | Назначение |
|---|---|---|
| `BOT_TOKEN` | да | Токен Телеграм-бота от [@BotFather](https://t.me/BotFather). Обязателен всегда, в том числе при `BOT_ENABLED=false`. |
| `BOT_ENABLED` | — | `false` — не запускать long polling (канал на паузе). Задачи Shopify работают как обычно. |
| `IMPORT_MODE` | — | `app` (по умолчанию) или `api`. |
| `SHOPIFY_SHOP` | для Shopify | Домен магазина, напр. `italian-edit.myshopify.com`. |
| `SHOPIFY_ADMIN_TOKEN` | * | Постоянный Admin-токen (`shpat_…`, легаси-приложения). |
| `SHOPIFY_CLIENT_ID` / `SHOPIFY_CLIENT_SECRET` | * | Client credentials (Dev Dashboard 2026+): клиент сам берёт токен на 24 ч. |
| `SHOPIFY_WEBHOOK_SECRET` | — | Секрет подписи вебхуков заказов Shopify. |
| `SERPER_API_KEY` | — | Google-поиск через serper.dev (2500 запросов бесплатно); без него — DuckDuckGo. |
| `DEFAULT_CURRENCY` | — | Валюта по умолчанию, если менеджер не указал символ (по умолчанию `EUR`). |
| `ALERT_CHAT_ID` | — | chat_id ТГ-группы для алертов об ошибках (узнать: команда `/chatid`). |
| `DATABASE_URL` | для api | PostgreSQL (нужна только режиму `api`). |
| `BG_EMAIL` / `BG_PASSWORD` / `BG_STORE_ID` / `BG_BASE_URL` | для api | Доступ к REST API BrandsGateway (Shopwoo). |
| `INVENTORY_CAP` | — | Правило «отдавать 1»: максимум остатка в Shopify (по умолчанию `1`). |
| `SHOPIFY_PUSH_BATCH` | — | Сколько товаров заливать за проход (по умолчанию `25`). |

\* Для Shopify нужен **либо** `SHOPIFY_ADMIN_TOKEN`, **либо** пара
`SHOPIFY_CLIENT_ID`+`SHOPIFY_CLIENT_SECRET` (см. `src/shopify/client.ts`).

## Сервер: фоновые задачи (планировщик)

`src/index.ts` регистрирует задачи в зависимости от режима. Простой планировщик
(`src/scheduler.ts`) гоняет их по интервалу; падение задачи шлёт алерт в ТГ, но
не роняет процесс.

| Задача | Режим | Интервал | Что делает |
|---|---|---|---|
| `bg-status-sync` | api | 5 мин | Синк остатков/статусов BG → БД (с учётом `INVENTORY_CAP`). |
| `bg-delta-sync` | api | 15 мин | Догрузка изменённых товаров BG → БД. |
| `bg-tracking-poll` | api | 30 мин | Опрос трек-номеров заказов, уведомления. |
| `shopify-push` | api | 1 мин | Заливка новых/изменённых товаров из БД → Shopify (батч). |
| `shopify-tagger` | **app** | 10 мин | **Дотегирует товары приложения складом `EU`/`US` по бренду + `designer:*`.** Идемпотентно. |
| `shopify-categorizer` | оба | 15 мин | Проставляет поля **Category** (таксономия Shopify) и **Product type** по категорийным тегам. Только дописывает пустое. |
| `shopify-descriptions` | **app** | 30 мин | Пересобирает описания товаров BG в человеческую вёрстку. Оригинал сохраняет в метаполе. Товары бота не трогает. |
| `shopify-expire-new` | оба | 6 ч | Снимает тег `new` с товаров старше 14 дней (коллекция New). |

## Телеграм-бот

> **Канал на паузе (с 1 августа 2026).** Товары из Италии руками сейчас не заводят,
> карточки в группе никто не ждёт. Код бота остаётся в проекте и запускается вместе
> с сервером — это решение по бизнесу, а не техническое отключение.
>
> Учесть при работе с проектом:
> - Выключается переменной **`BOT_ENABLED=false`** — тогда long polling не стартует.
>   На хостинге это не только экономия: см. про 409 Conflict в разделе о деплое.
> - `BOT_TOKEN` **всё равно обязателен**: без него `loadConfig()` бросает исключение
>   и процесс не стартует вовсе (`src/config.ts`). Убирать переменную с хостинга нельзя.
> - **Товары бота сняты с витрины 1 августа 2026.** Их было 6: три уже лежали
>   в архиве, три активных переведены в DRAFT. На витрине остались только товары BG —
>   это важно для блока про аутентичность на странице товара: утверждение
>   «connected to live supplier inventory» верно для BG и неверно для товаров бота,
>   заведённых вручную с сайтов брендов.
> - Товары бота продолжают обслуживаться задачами: `shopify-categorizer` проставляет
>   им Category, `shopify-expire-new` снимает `new`. Исключение — `shopify-descriptions`,
>   она обходит их по тегу `tg-bot` намеренно.
> - Открытые вопросы по боту (конвертация валют для compare-at, типы обуви и сумок
>   в `categorize.ts`) не горят, пока канал стоит.

**Формат сообщения менеджера** (каждая часть с новой строки, цена — последней):

```
Ophidia mini bag
beige and ebony Supreme
Gucci
1200
```

(без вариации — три строки: название / дизайнер / цена)

**Что делает бот** (`src/bot/bot.ts` → `src/search/findProduct.ts`):

1. Определяет официальный домен дизайнера (`src/search/brands.ts`).
2. Ищет товар (Serper → Google, либо DuckDuckGo) на этом домене.
3. Скачивает страницу, парсит **JSON-LD** (schema.org Product) или OpenGraph —
   один парсер покрывает большинство брендов без индивидуальных скраперов.
4. Отвечает карточкой: фото, описание, цена бренда (зачёркнута) vs наша цена.
5. **Создаёт черновик товара в Shopify** (`src/shopify/draftProduct.ts`):
   - статус **DRAFT** (на витрине не виден, пока менеджер не опубликует);
   - наша цена — цена товара; цена бренда — `compareAtPrice` (зачёркнутая «до скидки»),
     но **только если валюта совпадает** с валютой магазина (иначе «скидка» вводила бы
     в заблуждение — бот честно предупреждает об этом в карточке);
   - фото грузятся отдельно (`uploadImages.ts`) — CDN брендов блокируют серверы Shopify,
     поэтому качаем сами и отдаём как base64;
   - теги: `tg-bot`, `new`, `italian-edit`, `delivery:manual-italy`, `EU`,
     `designer:<бренд>`, категория (`category:*` из названия/URL), пол (по URL).

**Команды:** `/start`, `/help`, `/check <запрос>`, `/chatid` (узнать chat_id для алертов).
Бот реагирует и на обычные сообщения группы, если они похожи на формат запроса —
для этого у бота должен быть **выключен privacy mode** (`/setprivacy` → `Disable` в @BotFather).

## Заливка и дотегирование товаров в Shopify

**`buildTags()`** (`src/shopify/products.ts`) — единая сборка тегов для товаров BG:
`["bg", warehouseTag(склад), ...genderTags(пол), "designer:<бренд>"]`.

**Режим `api` — `shopify-push`:** берёт очередь из БД (`productsToPush`), для каждого
товара создаёт (`productCreate`, статус ACTIVE) или обновляет (`productUpdate`) товар,
ставит цену/SKU варианта и остаток на первой локации. Ошибка одного товара не
останавливает остальные; результат пишется в `sync_log`.

**Режим `app` — `shopify-tagger`** (`src/shopify/tagStoreProducts.ts`): приложение BG
залило товары само, но без склада. Задача находит товары **без** тега `EU`/`US`
(запрос `-tag:'EU' -tag:'US' status:active,draft`) и добавляет:
- склад `EU`/`US` — из бренда через `warehouseForBrand()`;
- `designer:<vendor>` — если ещё нет.

Только **добавляет** теги, ничего не удаляет; идемпотентно и **самовосстанавливается**
(если приложение BG затрёт теги при ресинке — вернёт на следующем проходе).

### Category и Product type — `shopify-categorizer`

Ни приложение BG, ни бот не заполняют поля товара **Category** (стандартная
таксономия Shopify) и **Product type**. Витрине они не нужны — навигация на тегах,
— но их читают фиды Google/Meta, расчёт налогов и маркетплейсы.

`src/shopify/category.ts` — единственный источник правды: сводит **оба** словаря
категорийных тегов к узлам таксономии Shopify.

| Источник | Формат тега | Пример → узел |
|---|---|---|
| приложение BG | иерархия через ` - `, частное слева | `Sandals - Shoes` → `aa-8-6` Sandals |
| приложение BG, 3-й уровень | уточняет, если у Shopify есть свой узел | `Slippers - Sandals - Shoes` → `aa-8-7` Slippers |
| бот | легаси `category:*` | `category:dresses` → `aa-1-4` Dresses |

Выбор победителя двухступенчатый, и порядок важен:

1. **Частность тега BG** (число сегментов). У товара висят разом `Shoes`,
   `Sandals - Shoes` и `Slippers - Sandals - Shoes` — прав самый длинный.
   Заодно гасится шум BG: паре сумок проставлены и `Accessories`,
   и `Shoulder Bags - Bags` — побеждает сумка.
2. **Глубина узла таксономии** — только при равной частности. Нужна тегам бота,
   где сегмент всегда один: `category:dresses` должен побить `category:clothing`.

Одной глубины узла мало: соседи по уровню неразличимы — у `Accessories` (`aa-2`)
и `Jewelry` (`aa-6`) она одинаковая.

Задача только **дописывает пустое** — категорию, выставленную менеджером вручную,
не перезаписывает (отсюда же идемпотентность). Незнакомый тег → поле остаётся
пустым, а название пишется в лог: проставить категорию наугад хуже, чем не
проставить — неверная молча портит фиды и налог.

Бот ставит `category`/`productType` сразу при создании черновика
(`draftProduct.ts`), не дожидаясь прохода задачи.

### Описания товаров — `shopify-descriptions`

Приложение BG отдаёт описание в **четырёх** разных видах — их накопал разбор
живого каталога, по одному примеру этого не понять:

| Вид | Как выглядит | Сколько было |
|---|---|---|
| Машинный шаблон | `Description:` + `Additional Info:`. Внутренние коды прямо в тексте для покупателя, грамматика не согласована («is a **sandals**») | 16 |
| Авторский текст | Настоящий абзац от бренда + хвост `Season / Fit / Composition` | большинство |
| Только характеристики | `<p>HANDBAG</p>` и хвост — прозы нет вовсе | несколько |
| Всё одним абзацем | `<br>` **с атрибутами**, часть фактов без двоеточия («Logo details») | 1 |

`src/shopify/description.ts` разбирает все четыре и собирает единую структуру:
абзац → **Details** → **Size & Fit** → **About the Brand** → **Style Code**.
Пустых заголовков не бывает: блок выводится, только если под него есть данные.

Принципиальные решения:

- **Авторский текст сохраняется дословно.** Живой абзац от бренда лучше любой
  фразы, собранной из спецификации. Шаблон включается, только если прозы нет.
- **Ничего не выдумываем.** В шаблонном абзаце нет ни одного оценочного слова —
  только факты поставщика. Блок About the Brand берётся из своего словаря
  (`brandBlurbs.ts`), бренда нет в словаре → блока просто нет, биографию
  ему не сочиняем.
- **Служебное вычищается**: MPN и коды артикулов из текста, `New collection: No`,
  `Gender` (дублирует тег), латинские названия сырья («Calf Leather ~~Bos Taurus~~»).
- **Style Code** — MPN: из шаблонной фразы, иначе из метаполя `shopwoo/_sw_mpn`.

Три предосторожности, без которых задачу нельзя пускать на живой каталог:

1. **Оригинал уходит в метаполе** `italian_edit.bg_description_raw` той же
   мутацией, что и перезапись. Перезаписав описание, исходник теряешь
   безвозвратно, а разбор ещё будет дорабатываться под новые виды фида.
2. **Товары бота исключены запросом** (`-tag:'tg-bot'`): у них настоящий текст
   бренда, он лучше всего, что соберётся из спецификации.
3. **Своя вёрстка узнаётся по классу** `ie-description` и второй раз не трогается.
   Затрёт приложение BG своим описанием — метки не будет, следующий проход
   пересоберёт (задача самовосстанавливается, как тегировщик).

## Заказы: Shopify → BrandsGateway

- **Режим `app`:** заказы BG-товаров передаёт **приложение BG само** — сервер не вмешивается.
- **Режим `api`:** вебхук `POST /webhooks/shopify/orders` (подпись проверяется по
  `SHOPIFY_WEBHOOK_SECRET`) → `forwardShopifyOrder()` оформляет заказ в BG и пишет в таблицу
  `orders`. Задача `bg-tracking-poll` подтягивает трек-номера и уведомляет.

Если заказ пришёл, а BG не настроен — сервер шлёт алерт в ТГ «оформите вручную».

---

## HTTP API

`src/api/server.ts` (Fastify), слушает `PORT` (по умолчанию 3000):

| Метод/путь | Назначение |
|---|---|
| `GET /health` | Проверка живости (для хостинга/мониторинга). |
| `POST /api/lookup` | Поиск товара: `{ title, designer, ourPrice, currency }` → `{ found, product, comparison }`. |
| `POST /webhooks/shopify/orders` | Вебхук заказов (только режим `api`, если задан секрет). |

## База данных

PostgreSQL нужна **только режиму `api`**; в режиме `app` сервер работает без неё
(бот и `shopify-tagger` в БД не заглядывают). Схема накатывается на старте из
`src/db/schema.sql`.

- **`products`** — каталог BG и его отражение в Shopify (цены оптовая/наша,
  склад `eu`/`us`, пол, `shopify_product_id`, статус, `push_error`, `manual_price`).
- **`orders`** — путь заказа Shopify → BG (bg_order_id, статус, трекинг).
- **`sync_log`** — журнал синхронизаций (видно, если что-то встало).

### Дизайнер над названием

Бренд идёт отдельной строкой над названием товара — и в карточке, и на странице
товара (`MIU MIU` / `BLACK CALFSKIN MID HEEL PUMPS`). Источник — поле **vendor**,
его заполняют оба канала: и приложение BG, и бот. Это только вывод: `title`
и `description` товаров не менялись, в админке, поиске, заказах и письмах
название остаётся прежним.

- **Карточки** — `blocks/product-title.liquid`: перед `product.title` выводится
  `<span class="product-designer">`. Правка в одном блоке покрывает все сетки
  (коллекции, главная, рекомендации, поиск). Строка прячется, если vendor пуст,
  равен имени магазина или уже стоит в начале названия — иначе вышло бы
  «GUCCI / GUCCI OPHIDIA BAG». Размер и регистр наследуются от пресета блока,
  бренд отличается только насыщенностью (600) и разрядкой.
- **Страница товара** — `templates/product.json`: в группе Header перед блоком
  заголовка добавлен text-блок `text_designer` с `{{ closest.product.vendor }}`
  (12px, uppercase). Отступ до `<h1>` задаёт `gap` группы Header — правится
  в редакторе темы.
- **Корзина и шторка корзины** — `snippets/cart-products.liquid`: бренд выведен
  отдельной строкой над названием тем же классом `product-designer`, так что
  оформление у него общее с карточками. Правила «спрятать, если совпал с именем
  магазина или уже стоит в начале названия» те же. Настройка блока `vendor`
  в расчёт не берётся: бренд — часть макета строки, а не необязательная добавка.

### Строка корзины

Строка в шторке и на странице корзины повторяет карточку страницы товара:
бренд жирным, под ним название, ниже **одной строкой вся цена** — наша чёрным,
прежняя серым и зачёркнутая, следом процент скидки. Под ценой — цвет и размер.

Справа, столбиком в верхнем углу строки, — сердце вишлиста и корзина
удаления. Сердце это общий сниппет темы `wishlist-button`, но с контекстом
`cart`: контекст `card` кладёт его absolute в белый круг поверх фотографии,
а неизвестный контекст даёт класс, под который правил в `wishlist.css` нет, —
остаётся голая иконка, размер ей задаётся на месте.

Чего в строке нет и почему:

- **Итога по строке.** Отдельная колонка справа при количестве 1 повторяла ту же
  цифру, а в макете её нет.
- **Выбора количества.** Его нет и на странице товара. Чтобы взять две штуки,
  товар добавляют дважды; удаление осталось.

**Размер переключается прямо в корзине** (`assets/ie-cart-variant.js`). Shopify
менять вариант у строки не умеет — `change.js` знает только количество и
свойства. Поэтому два запроса: сначала `add.js` с новым вариантом, потом
`change.js` с нулём на старую строку. Порядок важен дважды: если размер разобрали,
пока корзина висела открытой, добавление не пройдёт и корзина останется как была;
и если выбранный размер уже лежит в корзине, `add.js` склеит строки сам —
через `update.js` одним запросом количество задаётся абсолютным числом и одна
из двух строк потерялась бы.

Id варианта для каждого значения размера ищется **в Liquid** и уходит в разметку
готовым: браузеру не нужно знать матрицу вариантов. Размеры, которых нет
в наличии, показаны зачёркнутыми и не выбираются — корзина их не примет.

Перерисовку после смены делает тема: скрипт рассылает `CartLinesUpdateEvent`
с секциями из ответа, и `cart-items-component` обновляет и шторку, и страницу,
а шапка — счётчик.

**Цвет в корзине — из тега, как на странице товара**, и таблица «тег = цвет»
там продублирована: на PDP она лежит в настройках секции `ie-product`, а секция
и сниппет корзины друг друга не видят. Меняете список цветов в редакторе темы —
поправьте и в `snippets/cart-products.liquid`. Правильное решение — вынести
таблицу в настройки темы, чтобы источник был один.

### Размер скидки

Если у варианта `compare_at_price` выше цены, рядом с ценами выводится процент
скидки (`−20%`). Считается в `snippets/price.liquid` — это общий сниппет цены,
поэтому процент появляется везде сразу: карточки, страница товара, рекомендации,
quick add.

- Процент считается **до** money-форматирования, пока цены ещё числа в центах
  (ниже по коду они превращаются в строки), и округляется к ближайшему:
  240 / 1199 = 20.02% → `−20%`.
- Элемент лежит внутри `.price__sale`, поэтому у товаров без скидки не рендерится.
- При смене варианта `assets/product-price.js` заменяет весь `priceContainer`
  свежим серверным HTML — процент пересчитывается сам и не устаревает.
- Объёмные цены (quantity price breaks) процент не показывают: там цена —
  диапазон, и одно число вводило бы в заблуждение. Для этого каталога
  breaks не настроены.

Бейдж на картинке остался прежним словом `Sale` — он рисуется отдельно
от цены и процент не дублирует.

**Корзина считает процент отдельно.** Общий `price.liquid` там не участвует —
у `snippets/cart-products.liquid` своя разметка цены, и процент добавлен в неё
по тому же правилу. Сравниваются ровно те два числа, которые выводятся рядом
(`item.final_price` против `compare_at_price` варианта или `original_price`),
иначе процент разошёлся бы с зачёркнутой ценой на строках со скидкой заказа.

### Формат цен: без «.00»

Круглые суммы выводятся без дробной части (`$1,900`), а ненулевые копейки
показываются полностью (`$1,900.50`). Делает это штатный фильтр Shopify
**`money_without_trailing_zeros`** вместо `money` — по документации, при
ненулевой дробной части его вывод совпадает с `money`.

Округлять при этом нечего: Shopify держит цену целым числом в минорных единицах
(центах), третий знак после запятой до темы не доезжает.

Заменено в двух файлах:

- `snippets/price.liquid` — цены товаров: карточки, страница товара,
  рекомендации, quick add, а также `unit_price`;
- `snippets/price-filter.liquid` — **только видимый текст**: активный диапазон
  у заголовка фильтра и подсказка «The highest price is …».

> **В фильтре цен `value` / `placeholder` / `data-min` / `data-max` /
> `data-range-max` менять нельзя.** Это машинные значения: их разбирает
> `convertMoneyToMinorUnits` из `money-formatting.js`, и он ориентируется
> на фиксированное число знаков после точки по разрядности валюты. Убрать там
> «.00» — сломать фильтр. Предупреждение об этом стоит комментарием в файле.

> Ветка `use_currency` (показ кода валюты рядом с ценой) осталась на
> `money_with_currency`: парного фильтра `money_with_currency_without_trailing_zeros`
> в Shopify нет, а собирать формат с кодом валюты вручную — значит разойтись
> с настройкой магазина. Сейчас показ кода выключен, так что ветка неактивна;
> если её включат, «.00» вернётся.

**Корзина и checkout не менялись.** Там `| money` как было, то есть
`$1,900.00`. Checkout вообще не правится без Shopify Plus, поэтому полного
единообразия не будет никогда — и это скорее к лучшему: в каталоге цены
читаются чище, а в корзине и оплате сумма видна до копейки. Если нужно
и в корзине без «.00» — это `snippets/cart-products.liquid`
и `snippets/cart-summary.liquid`, там 14 мест.

### Валюта и рынки

Витрина показывает **евро**, а база магазина — **доллар**. Это не противоречие,
а конструкция из двух слоёв, и путать их дорого.

| Слой | Значение | Где смотреть |
|---|---|---|
| База магазина | **USD** — в ней хранятся цены товаров, считаются отчёты и выплаты | Settings → General → Currency display |
| Рынок **International EUR** | **EUR**, 27 регионов, Dynamic FX, статус ACTIVE | Settings → Markets |
| Рынок **United States** | USD, статус **DRAFT** — неактивен | Settings → Markets |
| Backup Region | **Italy** — настройки для посетителей вне активных рынков | Settings → General |

Активный рынок один, поэтому **евро видят все**, включая посетителей из США:
рынок United States в черновике, значит американец попадает не в него, а в backup
region (Италия) и получает евро.

Два следствия, которые стоит держать в голове:

- **Цены на витрине плавают с курсом.** Число хранится в долларах, евро получается
  пересчётом Dynamic FX. Товар, заведённый как 1900, сегодня показывается одной
  суммой, завтра другой. К формату «без .00» в теме это отношения не имеет — там
  только вывод, а скачет сама величина.
- **`DEFAULT_CURRENCY=USD` на сервере — это правильно.** Переменная описывает базу
  магазина, а не то, что видит покупатель. Ставить туда `EUR`, глядя на витрину, —
  ошибка: сломается сравнение валют в `draftProduct.ts`.

> **Отсюда же открытый вопрос №1 про compare-at.** Бренды публикуют цены в евро,
> база магазина — доллар, а зачёркнутая цена ставится только при совпадении валют.
> Значит на европейских брендах она не появляется почти никогда. Чинится не сменой
> валюты, а конвертацией по курсу в момент создания черновика.

### Коллекции

- **Дизайнерские** (Gucci, Prada, Miu Miu, The Row, …) — по правилу **Vendor = бренд**.
  Есть отдельная индекс-страница дизайнеров.
- **Категорийные** (Bags, Shoes, Clothing и подкатегории, Accessories) — по тегам
  (тег приложения BG `Bags`/… ИЛИ легаси `category:*` от бота).
- **Типы обуви** (Sneakers, Flats, Loafers, Pumps & Heels, Sandals, Boots) — по
  тегам второго уровня BG (`Sneakers - Shoes` и т.д.), на них держится выпадающее
  меню под SHOES.
- **Типы сумок** (Handbags, Shoulder Bags, Clutch Bags) — так же, по
  `Handbags - Bags` и т.д., для меню под BAGS. Словарь BG здесь беднее: три
  подтипа против шести у обуви. Totes и Backpacks не заводили — таких тегов
  у BG не встречалось, а тоут и рюкзак в каталоге есть только от бота.

> У подколлекций обуви и сумок **нет легаси-тега бота**: его словарь
> (`categorize.ts`) знает только `category:shoes` и `category:bags` без дробления
> на типы. Поэтому обувь и сумки, заведённые ботом, попадают в `Shoes`/`Bags`,
> но ни в одну подколлекцию. Сейчас это 1 обувь и 4 сумки. Станет заметно, когда
> ботом начнут заводить их всерьёз — тогда добавить типы в `categorize.ts`
> и вторым тегом в правила.
- **New** — по тегу `new`; товар выпадает через 14 дней (job `shopify-expire-new`).
- **Ships from Europe / USA** — по тегам `EU` / `US`.
- **Women / Men** — по тегам `Women` / `Men`.

Скрипт `scripts/setup-collections.ts` создаёт/чинит служебные коллекции
(`Italian Edit`, `Ships from Europe/USA`, `Women`, `Men` — теги берутся из тех же
`warehouseTag()`/`genderTags()`, что тегируют товары, чтобы витрина и товары
не разошлись по формату) **и категорийные**. Дизайнерские настраивались напрямую,
не этим скриптом.

> **Категорийная коллекция обязана ловить оба формата тегов** — приложения BG
> и легаси-формат бота, через ИЛИ (`appliedDisjunctively`). Без первого коллекция
> пустует при импорте BG, без второго теряет товары бота. На этом уже обожглись:
> у `Jewelry` правило было только под бота (`category:jewelry`), и коллекция стояла
> пустой, хотя товар с тегом BG `Jewellery - Accessories` в каталоге лежал.
>
> Теги BG в скрипте выписаны с фактических товаров. Помеченные `/* ? */` —
> предположение по образцу соседей: таких товаров в каталоге ещё не было
> (Shorts, Swimsuits, Lingerie, Pajamas, Matching Sets). Ошибка там безвредна —
> коллекция и так пуста, — но и полагаться на них нельзя, пока не проверим
> на живом импорте. У `Kids` тег BG не выдумывали вовсе: похоже, у поставщика
> это отдельное измерение, а не категория.

### Карусель дизайнеров

Coverflow-карусель карточек дизайнеров (в стиле Saks) под баннером-героем на главной:
соседние карточки уходят за активную, скролл зациклен.

**Источник слайдов — на выбор.**

- *Автоматически* (как было): коллекции с метаполем `custom.designer_index`,
  картинка из `collection.image` → фото первого товара → фирменный фолбэк
  с именем. Новый дизайнер с флагом появляется сам.
- *Вручную*: слайды-блоки, до 20 штук. У слайда указывается **коллекция**,
  куда ведёт клик, и при желании **тег**, которым её сузить — ссылка
  собирается сама маршрутом `/collections/<коллекция>/<тег>`, тем же, которым
  фильтрует переключатель в шапке. Тег прогоняется через `handleize`:
  в адресе он живёт хендлом, а в настройке его пишут как у товара
  («Miu Miu» → `miu-miu`).

  Фото и подпись, если их не задали, берутся у той же коллекции (изображение
  коллекции → фото первого товара). Поэтому слайд «Gucci» делается одним
  выбором коллекции: остальное подтянется.

  Поле «Ссылка вручную» перебивает коллекцию и тег — на случай, когда вести
  надо не в каталог, а на страницу или наружу. Ни ссылки, ни коллекции —
  карточка не кликается.

Ширина карточки в обоих режимах задаётся настройкой (по умолчанию 420px);
на узких экранах карточка всё равно ужимается по ширине экрана. Потолок
приходит в CSS инлайновой переменной: блок `{% stylesheet %}` собирается
один раз на тему и настроек секции не видит.

Разметка карточки — общий сниппет `ie-designer-card`, чтобы два источника
не разъехались по вёрстке.

В редакторе темы пустая карусель показывает подсказку вместо пустоты:
переключил источник — и всё исчезло читается как поломка. На витрине
подсказки нет, там пустая секция просто не рисуется.

Насколько сосед выглядывает — настройка секции **Side cards visible** (по умолчанию
50%, то есть ровно половина). Геометрия тут не на глаз: сосед видён наполовину, когда
его *центр* стоит точно на краю активной карточки, то есть при сдвиге ровно 50% ширины —
и это не зависит от масштаба соседа. Отсюда пересчёт настройки в сдвиг:

```
сдвиг = 50% + s₁ × (видимая доля − 50%),   s₁ = 0.9 — масштаб соседа
```

`s₁` задан в CSS как `--dc-scale-step` (0.1 на шаг). **Меняете шаг масштаба — правьте
коэффициент и в Liquid**, иначе подпись настройки разойдётся с картинкой.

На телефоне карточка уже (62vw против 420px на десктопе): коверфлоу требует по
горизонтали около двух ширин карточки, и при прежних 74vw соседей обрезал край экрана,
а не активная карточка — половины не выходило ни при каком сдвиге. При 62vw видно ~34%.
Это осознанный обмен размера активной карточки на видимость соседей; полные 50% на
телефоне потребовали бы ~52vw.

### Вишлист

Целиком в теме, без приложений и без нашего сервера.

**Хранение — `localStorage`**, ключ `italian-edit:wishlist`, массив хендлов товаров.
Отсюда главное ограничение, которое надо знать заранее: **список не переезжает между
устройствами и не привязан к аккаунту.** Сохранил с телефона — на ноутбуке пусто.
Иначе и нельзя: синхронизация по покупателю требует записи в его метаполя, а на это
нужен либо платный апп, либо свой сервер с прокси. Апгрейд не потребует переделки
витрины — достаточно подменить `read`/`write` в `wishlist.js` на запросы к серверу,
компоненты их не видят.

| Файл | Что делает |
|---|---|
| `assets/wishlist.js` | Хранилище + три веб-компонента: `wishlist-button`, `wishlist-count`, `wishlist-grid` |
| `assets/wishlist.css` | Все стили вишлиста |
| `snippets/wishlist-button.liquid` | Одна разметка на два вида: `card` (сердце) и `product` (кнопка с подписью) |
| `sections/wishlist.liquid` | Страница вишлиста: пустая оболочка + состояния |
| `sections/wishlist-card.liquid` | Собирает настоящую карточку витрины; только для Section Rendering API |
| `blocks/wishlist-button.liquid` | Блок для страницы товара — двигается в редакторе темы |
| `templates/page.wishlist.json` | Шаблон страницы |

Где появляется: сердце в верхнем-**левом** углу каждой карточки (правый занят бейджем
скидки), кнопка под «в корзину» на странице товара, иконка со счётчиком в шапке,
страница `/pages/wishlist`.

Удаление — **повторным нажатием на то же сердце**. Отдельной кнопки в вишлисте нет:
на странице стоят те же карточки витрины, у них сердце уже есть, и оно там всегда
в залитом состоянии. Сетка перерисовывается по событию `wishlist:change` и сама
выкидывает снятую карточку.

**Как собирается страница вишлиста.** Сама секция отдаётся пустой и спокойно кешируется
CDN — список у каждого свой. Карточки JS добирает поштучно через Section Rendering API:
`/products/<handle>?section_id=wishlist-card`. Складывать в разметку весь каталог и
прятать лишнее нельзя: сегодня это 90 карточек на каждый просмотр, а на полном каталоге
BrandsGateway — десятки тысяч.

**Карточка — настоящая, не копия.** Своей вёрстки у `wishlist-card.liquid` нет: сниппет
`product-card` даёт оболочку (вместе с сердцем), а начинку собирают те же блоки темы, что
в `templates/collection.json`, — галерея, название, цена, свотчи. Поэтому в вишлисте
работают слайдшоу, бейдж скидки и быстрое добавление, а правки карточек на витрине
доезжают сюда сами.

Блоки вызываются поштучно через `content_for 'block'`. Это третий подход из трёх — два
других закрыты, и оба проверены на живом магазине, чтобы не проверять снова:

1. **Блоки из `presets` при section-rendering не разворачиваются** — приходил пустой
   контейнер в 201 байт.
2. **Положить дерево блоков в `templates/product.json` нельзя**: Shopify отвечает
   `Section id 'wishlist-card' must exist in order`, а попадание в `order` означало бы
   лишнюю карточку на каждой странице товара.

Спасает то, что все четыре нужных блока листовые (`blocks: {}`) — дефолтных настроек
достаточно, чтобы они отрисовались. Дефолт галереи — `portrait` (4/5), ровно как на
витрине.

**Чего дефолты не дают — восстановлено в `wishlist.css`.** `content_for 'block'` не умеет
передавать настройки блока, а на витрине у названия стоит пресет `h5`, у цены `h6`: 13px
капсом против 15px без капса на дефолтах. Разница видна глазом, поэтому пресет
воспроизведён — но **ссылками на переменные темы** (`--font-h5--*`), а не числами, чтобы
правка шрифтов в редакторе доезжала и сюда. Там же продублирован стиль `.product-designer`
(`display: block`, вес 600): он единственный, чей `{% stylesheet %}` в ответ
section-rendering не попадает вовсе — без него бренд слипался с названием в одну строку.
Промежуток карточки передаётся параметром `product_card_gap: 4` — сниппет берёт его из
настроек своего блока, а мы зовём его без блока.

Сетка тоже не на глаз: `340px` — это значение из `util-product-grid-card-size.liquid` для
`centered` + `large`, как стоит секция коллекции. Проверено на двух ширинах: 1190px даёт
`386 × 3`, 1269px — `412 × 3`, совпадает с каталогом. На телефоне — `189 × 2` при gap 12px
и во всю ширину экрана: секция коллекции стоит с `full_width_on_mobile`, а страница
вишлиста `page-width`, и тема на телефоне сама сжимает промежуток.

**Стили карточки переносит JS.** В ответе section-rendering едет
`<style data-section-stylesheet>` на ~50 КБ (галерея, бейджи, слайдшоу, быстрое
добавление), и лежит он **вне** `<li>`. `adoptStyles` в `wishlist.js` копирует его в
документ с дедупом по содержимому. Без этого карточки приезжали неоформленными: бейдж
«Sale» растягивался в полосу во всю карточку, быстрое добавление вставало в поток,
стрелки слайдшоу торчали в углу.

Хендл, а не id, — потому что этот адрес требует хендла. Плата: **переименование товара
роняет его из вишлиста.** Такой хендл вычищается сам, но проверять надо не код ответа:
на несуществующий товар Shopify отдаёт **200 и пустую обёртку секции** (~74 байта), а не
404. Проверено на живом магазине; в `fetchCard` судим по наличию `[data-wishlist-card]`
в ответе.

Страница закрыта от индексации (`noindex, follow` в `meta-tags.liquid`): на сервере она
пуста, в выдаче это тонкая страница. Иконка в шапке рисуется только если страница
существует и опубликована, — иначе висела бы ссылка на 404.

### Публикация правок темы

MCP-коннектор Shopify **не может писать в живую (опубликованную) тему** — только в
черновик. Порядок: продублировать тему → править черновик → менеджер публикует
вручную из админки.

Коммерческие условия вынесены в один объект `TERMS` наверху файла — срок сборки,
сроки доставки по регионам, окно возврата, кто платит обратную пересылку. Меняются
там, во всех текстах подставляются сами.

Что учтено под наш бизнес (в готовых шаблонах этого нет):

- **Отгрузка с нескольких складов.** В Shipping сказано, что заказ может приехать
  разными посылками без доплаты. В Refund — что адрес возврата **надо запросить
  заранее**: он у каждой вещи свой, и посылка, отправленная не туда, теряется.
- **Пошлины.** Юрлицо в США, товар едет из ЕС — границу пересекает. Пошлины платит
  получатель, возвращает их таможня, а не мы.
- **Право на отказ по правилам ЕС** — отдельным разделом: 14 дней обязательны для
  покупателей из ЕС, и оговорка о них важнее, чем удобство формулировок.
- **Товарные знаки.** В Terms прямо сказано, что мы не авторизованный ритейлер
  брендов и знаки принадлежат владельцам.

> **Юрист тексты не проверял.** Это рабочие черновики под конкретную модель
> магазина, а не заключение. Перед серьёзными объёмами продаж стоит показать
> их юристу — особенно раздел про ЕС.

**Публикация.** Нужен скоуп `write_legal_policies`; у приложения из `.env` его
нет, поэтому `--apply` отвечает отказом. Пока скоупа нет:

```bash
cd server && npx tsx scripts/setup-policies.ts --export
```

Файлы лягут в `docs/policies/*.html`, оттуда вставляются в Settings → Policies.
На витрине они же собраны в колонку подвала — меню `terms-and-policies`
(см. [«Подвал»](#подвал)).
Когда скоуп добавят в Dev Dashboard — заработает `--apply` и ручной шаг уйдёт.

### Оформление на витрине

Страницы `/policies/*` рендерит **сам Shopify**, а не секция темы: разметка
приходит готовой (`.shopify-policy__container > .shopify-policy__body > .rte`),
и вместе с ней грузится служебный `policy-*.css` с `max-width: 65ch`
и центрованным заголовком. Шаблона тут нет — только переопределение стилей.

Оформление лежит в `assets/policy.css`, подключается из `snippets/stylesheets.liquid`
после `base.css`. Оттуда же в `:root` прокидываются `--brand-*` из
`settings.color_palette`: на страницах политик переменные цветовой схемы темы
недоступны, а держать вторую копию бренд-цветов в CSS — верный способ разъехаться
с палитрой.

Что сделано по брендбуку: заголовок бордовый (`color1` = `#4E070D`), выровнен
влево и отчёркнут тонкой линией; подзаголовки — Source Serif 4 бордовым, капсом
с разрядкой; текст 17px с интерлиньяжем 1.75; маркеры списков и ссылки бордовые;
контактный блок в конце — на кремовой подложке (`color3`).

Три подводных камня, на которых это ломалось:

1. **Ширина.** `main.content-for-layout` — flex-контейнер, а flex-элемент без
   `width` ужимается по содержимому и до `max-width` не дотягивается. Без
   `width: 100%` колонка так и оставалась 556px вместо 832.
2. **Ограничитель у абзацев.** С `max-width: 62ch` на `p` расширение контейнера
   доставалось только рамке, а текст оставался прежней ширины. Ограничителя
   намеренно нет — ширину задаёт только контейнер.
3. **Кремовая подложка.** По правилу «последний абзац» она на странице Contact
   попадала на оговорку про адрес, а не на контакты. Привязана к `:has()`
   с `mailto` — бьёт точно. Браузер без `:has()` просто не покажет подложку.

### Хостинг: Render

Сервер должен работать как **постоянный процесс**: пока он крутится, фоновые задачи
идут сами; остановится — встанет и дотегирование новых товаров.

Живёт на Render как Web Service **`italianedit`** (Frankfurt):
[italianedit.onrender.com](https://italianedit.onrender.com).

| Настройка | Значение |
|---|---|
| Root Directory | `server` |
| Build Command | `npm install --omit=dev` |
| Start Command | `npm run start` |
| Health Check Path | `/health` |
| Instances | 1 |

Версия Node не задаётся в панели — Render читает `engines.node` из `package.json`.

Четыре решения, каждое из-за конкретных граблей:

1. **Не бесплатный тариф.** Render Free усыпляет сервис после 15 минут без
   **входящих** HTTP-запросов. Бот на long polling создаёт только исходящие,
   так что для Render он выглядит бездействующим — уснёт вместе с задачами.
2. **`npm install --omit=dev`, а не `npm ci`.** Лок сгенерирован на Windows и на
   Linux `npm ci` не проходит: в дерево там добавляется `@emnapi/runtime`
   (peer-зависимость `@napi-rs/wasm-runtime` ← `rolldown` ← `vite` ← `vitest`),
   в локе его нет, и `npm ci` отказывается ставить что-либо. Вся эта цепочка —
   девелоперская, в проде не нужна, поэтому прод-установка её просто не трогает.
   Заодно сборка идёт секунду вместо минуты. Вернуть `npm ci` можно, но для этого
   нужен лок, собранный на Linux (WSL/Docker/CI).
3. **`tsx` в `dependencies`, а не в dev.** `npm run start` запускается через него,
   а прод-установка девзависимости пропускает — иначе `tsx: not found`.
   Пакет `typescript` при этом не нужен: внутри `tsx` свой esbuild.
4. **Ровно один инстанс.** Два процесса с одним `BOT_TOKEN` дают от Telegram
   409 Conflict, и long polling ломается у обоих. По той же причине нельзя
   держать локальный `npm run dev`, пока работает хостинг.

> **409 Conflict случается на каждом деплое — это нормально.** Render выкатывает
> без простоя: поднимает новый процесс, **не убив старый**. Пока они живут внахлёст,
> Телеграм видит два `getUpdates` с одним токеном и отвечает 409 тому, кто пришёл
> вторым. Старый умирает через секунду, и следующая попытка проходит.
>
> Опасен тут не сам 409, а то, во что он обходился раньше: реджект `bot.start()`
> оставался необработанным, и Node убивал **весь процесс** — вместе с HTTP API и
> четырьмя задачами Shopify, которые к Телеграму отношения не имеют. Спасал только
> автоперезапуск Render. Теперь ошибка поллинга ловится в `src/index.ts`: бот
> останавливается и шлёт алерт, сервер продолжает работать.
>
> Пока канал бота на паузе, надёжнее просто не поллить — поставьте на хостинге
> `BOT_ENABLED=false`, и класс проблем уходит целиком.

**Переменные окружения** задаются в панели Render (Environment), `.env` в репозиторий
не коммитится. Нужны: `BOT_TOKEN`, `IMPORT_MODE=app`, `SHOPIFY_SHOP`,
`SHOPIFY_CLIENT_ID`, `SHOPIFY_CLIENT_SECRET`, `SERPER_API_KEY`, `DEFAULT_CURRENCY=USD`.

Две переменные из локального `.env` переносить **нельзя**:

- **`DATABASE_URL`** — там `localhost`, а на хостинге это сам контейнер, и никакой
  базы по этому адресу нет. В режиме `app` она не нужна вовсе — переменную просто
  не заводят. Если всё же уехала, в логах будет `ECONNREFUSED … 127.0.0.1:5432`:
  сервер это переживёт (предупредит и поедет дальше), но переменную надо убрать.
  В режиме `api` недоступная база, наоборот, валит старт намеренно — работать
  без каталога и заказов хуже, чем не подняться.
- **`PORT`** — Render задаёт свой (10000), `loadConfig()` его читает. Локальные 3000
  на хостинге не «ломают» сервис сразу: Render находит открытый порт и поднимает
  сервис на нём. Но сетевая конфигурация настраивается под найденный порт, и при
  его смене Render перезапускает деплой (`New primary port detected …`). Переменную
  не заводят — портом управляет хостинг.

> **Молчаливый отказ, который легко пропустить.** Если `SHOPIFY_SHOP` или пара
> client credentials не доехали, `loadConfig()` оставляет `config.shopify` пустым,
> а `src/index.ts` регистрирует все четыре задачи под условием `if (shopifyClient)` —
> ошибки не будет, задачи просто не появятся. Единственный признак в логах:
>
> ```
> Планировщик: задач нет (ждём креды BrandsGateway).
> ```
>
> Здоровый запуск выглядит так:
>
> ```
> Планировщик: shopify-tagger, shopify-descriptions, shopify-categorizer, shopify-expire-new
> ```

> **Правка переменных требует рестарта.** Node читает окружение только при старте.
> Сохранение в панели само по себе процесс не перезапускает — нужен
> Manual Deploy → Deploy latest commit. Проверить, что рестарт случился, можно по
> `uptime` в `/health`: если он больше времени, прошедшего с правки, работает старое
> окружение.

> **Деплой только вручную — это решение, а не недоделка.** Render клонирует
> репозиторий анонимно («we don't have access to your repo, but we'll try to clone
> it anyway»): он публичный, поэтому сборка проходит, но вебхуков от GitHub нет,
> и коммиты сами в прод не уезжают. Выкатывает человек — Manual Deploy → Deploy
> latest commit. Доступ Render к репозиторию **выдавать не нужно**: пуш в `main`
> не должен автоматически становиться продом.
>
> Практическое следствие: после любого коммита изменения на хостинге не появятся,
> пока кто-то не нажмёт кнопку. Проверить, какой коммит сейчас работает, можно
> в шапке лога деплоя («Checking out commit …»).

**Проверка после деплоя:**

```bash
curl https://italian-edit-server.onrender.com/health
```

Ответ `{"ok":true,"uptime":…}`, дальше — строка `Планировщик:` в логах с четырьмя
задачами, и через 10 минут первый проход тегировщика.

> **Алерты пока никуда не идут.** `ALERT_CHAT_ID` не задан, поэтому упавшая фоновая
> задача сообщит об этом только в лог Render. Локально это было неважно, на хостинге
> за задачами никто не смотрит глазами. Завести: добавить бота в группу, написать
> там `/chatid`, положить полученное число в переменную.

## Операционные заметки (runbook)

**Прогнать `shopify-tagger` разово (не дожидаясь 10-минутного цикла).**
Например, после массового импорта в приложении BG. Создать во `server/` временный файл:

```ts
// server/_run-tagger.ts
import "dotenv/config";
import { loadConfig } from "./src/config";
import { ShopifyClient } from "./src/shopify/client";
import { tagStoreProducts } from "./src/shopify/tagStoreProducts";

const config = loadConfig();
const client = new ShopifyClient(config.shopify!);
console.log(await tagStoreProducts(client, { maxProducts: 500 }));
```

```bash
cd server && npx tsx _run-tagger.ts && rm _run-tagger.ts
```

Авторизация возьмётся из `.env` (client_credentials, если нет `SHOPIFY_ADMIN_TOKEN`).

> **Лаг индекса.** После массового `tagsAdd` Shopify `productsCount`/фильтры
> обновляются с задержкой ~минуту — доверяйте отчёту задачи (`tagged`/`failed`),
> а не мгновенному счётчику.

**Проверить, что коллекции Ships from наполнены:** товар должен нести тег `EU`/`US`.
Если `/collections/all/US` пуст — просто нет US-товаров (все текущие бренды — EU).

## Открытые вопросы

1. **Конвертация валют для compare-at.** Если цена бренда в EUR, а магазин в USD,
   зачёркнутая цена может вводить в заблуждение. Бот сейчас ставит compare-at только
   при совпадении валют. Автоконвертацию — обсудить и внедрить.
2. **US-сток.** У всех текущих товаров бренды европейские → фильтр `US` пуст. Чтобы
   появились «американские» товары, нужен реальный US-источник: либо US-склад BG
   (сверить список брендов в `warehouseByBrand.ts` с фактическим каталогом BG), либо
   отдельный US-поставщик (техника под `warehouse: "us"` уже готова).
3. **Словарь категорий BrandsGateway.** Соответствие в `src/shopify/category.ts`
   собрано по товарам, которые уже приходили (обувь, одежда, сумки, аксессуары
   Miu Miu). Категории, которых в каталоге ещё не было — купальники, бельё, шорты,
   пижамы, комплекты, детское — не проверены: их теги BG мы не видели. При импорте
   новых разделов смотреть лог `shopify-categorizer` («категория не опознана»)
   и дописывать правила. Там же — теги `/* ? */` в `setup-collections.ts`.
4. **Названия товаров от BG.** Описания вычищены (`shopify-descriptions`),
   а вот заголовки — нет: «Brown Lamb **Ovis Aries Aries** Handbag»,
   «Gray Wool **Oves Aries** Dress Pants» (там ещё и опечатка поставщика),
   «Multicolor Calf Leather **Bos Taurus** Slip-On Loafers». Чистилка
   `stripLatinSpecies` в `description.ts` уже есть — нужен проход по `title`.
   Отдельный вопрос: переписывать заголовок рискованнее описания, он участвует
   в handle товара и в ссылках.
5. **Скоуп `write_legal_policies`.** Пока его нет у приложения, правовые страницы
   публикуются вставкой из `docs/policies/` руками. Добавить скоуп в Dev Dashboard —
   и `setup-policies.ts --apply` закроет этот шаг.
6. **Ссылка на политики в описании товара.** В образце карточки была строка
   «Learn more about our shipping and returns policy». Выводить её правильнее
   в теме один раз, а не дублировать в 85 описаний — сделать после публикации
   страниц.
7. **Вишлист без синхронизации.** Список лежит в `localStorage`, то есть привязан
   к браузеру: между телефоном и ноутбуком не переезжает, при чистке данных
   пропадает, и в аналитике его не видно. Для нового магазина это нормальный
   старт, но как только появятся регулярные покупатели с аккаунтами — переносить
   в метаполя покупателя. Точка вмешательства одна: `read`/`write` в
   `assets/wishlist.js`.
8. **Вишлист повторяет каталог значениями, а не связью.** Раскладка и настройки
   блоков карточки живут в секции `main-collection` и в `templates/collection.json`,
   а достучаться до них из секции, которую дёргают через section-rendering, нечем
   (см. два закрытых подхода выше). Поэтому в `wishlist.css` продублированы:
   размер карточки `340px`, промежутки 16/12px, гашение бокового отступа на
   телефоне, пресет типографики и стиль `.product-designer`. Поменяете в редакторе
   размер карточек коллекции, `full_width_on_mobile` или пресеты названия/цены —
   вишлист сам за ними не пойдёт. Шрифты частично исключение: они взяты
   переменными `--font-h5--*` и поедут следом.
9. **Тексты вишлиста захардкожены по-английски** («Add to wishlist», «Your wishlist
   is empty») — в `locales/*.json` не заведены. Магазин англоязычный, но при
   добавлении второго языка эти строки не переведутся.
```
